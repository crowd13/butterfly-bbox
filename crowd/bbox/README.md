# Запуск bbox

Правила и бюджет — в [архитектуре](ARCHITECTURE.md).
Форматы эталонов, готовности и аудита — в [fixtures/README.md](fixtures/README.md).
Нужен Python 3.10+; команды выполняйте из корня репозитория в Bash или Zsh.

## 1. Окружение и план

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r crowd/bbox/requirements.txt

export BBOX_RUN='crowd/bbox/runs/pilot'
mkdir -p "$BBOX_RUN"
bbox() { python3 -m crowd.bbox.project --run "$BBOX_RUN" "$@"; }
bbox plan
```

`bbox` — сокращение CLI с одним каталогом запуска. В новом терминале повторите
активацию окружения, переменную и определение функции. Справка: `bbox --help`.
Сверьте план и комиссию аккаунта. Настройки — в `config.json`; для своей копии
передавайте одинаковый `--config ПУТЬ` командам `plan`, `check`, `prepare`.

## 2. Данные и эталоны

Для подготовленного [банка эталонов](fixtures/gold/README.md) используйте
сохранённые 400 ID:

```bash
cp -n crowd/bbox/fixtures/gold/working_manifest.csv data/manifest_bbox.csv
```

Если файл уже существовал, сверьте его с сохранённым manifest: старые классы молей
нужно обновить. Для новой независимой выборки есть
`bbox select --output /путь/новый_manifest.csv` (303 целевых, 57 похожих, 40 фоновых).
Новый отбор может включить изображения из готового банка: для него заново
подбирают непересекающиеся эталоны.

Проверьте состав выборки, визуальные дубли и разнообразие пилота. `select`
не перезаписывает файлы. Скопируйте одобренный банк в каталог запуска:

```bash
cp crowd/bbox/fixtures/gold/gold.json "$BBOX_RUN/gold.json"
```

```bash
bbox check --manifest data/manifest_bbox.csv --fixtures "$BBOX_RUN/gold.json"
bbox prepare --with-training --manifest data/manifest_bbox.csv --fixtures "$BBOX_RUN/gold.json"
bbox preflight
bbox preview
```

**`prepare` фиксирует данные, настройки и интерфейс** в `inputs.json`.
Правки исходных файлов после этого не обновляют запуск. Не редактируйте снимок.
Для снимка, созданного до уточнения о молях, подготовьте новый запуск в новом
каталоге после проверки обновлённых эталонов.
`preflight` проверяет доступность, размеры и точные дубли изображений.

Для локального просмотра запустите:

```bash
python3 -m http.server 8765 --bind 127.0.0.1
```

Откройте `http://127.0.0.1:8765/crowd/bbox/runs/preview.html`; остановка сервера —
`Ctrl+C`. Другую фотографию можно выбрать через
`bbox preview --manifest /path/to/candidates.csv --photo-id 123`.
Для подготовки эталона перенесите `output_values` из «Проверить ответ» в
`solution` записи банка: редактор автоматически его не сохраняет.

## 3. Загрузка и проверка проекта

### Тест без модерации и выдачи

Для проверки API без возможности платной выдачи создайте отдельный запуск:

```bash
export BBOX_RUN='crowd/bbox/runs/api-test'
bbox prepare --test-only \
  --manifest crowd/bbox/fixtures/gold/working_manifest.csv \
  --fixtures crowd/bbox/fixtures/gold/gold.json
bbox create
bbox status
```

Перед `create` задайте `YANDEX_TASKS_OAUTH`. Это реальные ресурсы в аккаунте:
проект с пометкой «ТЕСТ» и закрытый экзаменационный пул.
Для отдельного обучения добавьте `--with-training` к `prepare`.
Режим допускает отсутствие человеческой проверки черновых эталонов,
но блокирует команды `ready`, `moderate` и `open`.
Для платного запуска подготовьте проверенные эталоны и новый каталог запуска
без `--test-only`. Не открывайте тестовый пул вручную в кабинете.

### Полная загрузка проекта

Чтобы загрузить отдельное обучение, экзамен и два закрытых рабочих пула:

```bash
export BBOX_RUN='crowd/bbox/runs/production'
bbox prepare --with-training \
  --manifest crowd/bbox/fixtures/gold/working_manifest.csv \
  --fixtures crowd/bbox/fixtures/gold/gold.json
bbox stage
bbox status
```

`--draft-gold` разрешает загрузить черновые эталоны, но `ready` всё равно требует
одобрения командой каждого эталона (`team_approval`). Такой запуск нужен для предпросмотра;
после проверки эталонов подготовьте новый запуск без этого флага.
Для проверенного запуска из шага 2 сразу выполните `bbox stage`.
Повтор команды продолжает загрузку без создания дубликатов.
В `status` обучение находится в `training`, будущие пулы — в `staged_batches`.
Все ресурсы остаются закрытыми; `stage` не отправляет их на модерацию.

### Рабочий запуск

Задайте OAuth-токен в переменной окружения `YANDEX_TASKS_OAUTH`, затем:

```bash
bbox create
bbox status
```

`create` загружает проект, навыки, обучение (если указан `--with-training`)
и **закрытый экзаменационный пул**. `stage` дополнительно загружает рабочие пулы.
ID проекта — в `state.json → resources.project`, пулов — в `status → batches`.

**Проверьте предпросмотр на платформе:** инструкцию, практику, рисование,
редактирование и удаление рамок, масштабирование и отправку всех типов ответа.
Не меняйте настройки проекта параллельно через кабинет.

Заполните `$BBOX_RUN/readiness.json`: `input_hash` из `status`, автор проверки,
результаты и фактическая комиссия. Затем:

```bash
bbox ready --file "$BBOX_RUN/readiness.json"
bbox moderate
```

**Дождитесь модерации в кабинете:** команда только отправляет пул на проверку.
Перед каждым `open` повторяйте `preflight`, если его результат старше суток.

## Ручное открытие пулов в кабинете

Для уже загруженного проекта можно управлять модерацией и открытием пулов
в кабинете, без `next-batch`, `open` и `release`. Выберите каталог именно этого
проекта и соответствующий токен в `YANDEX_TASKS_OAUTH`:

```bash
export BBOX_RUN='crowd/bbox/runs/production-token2-20261116'
bbox() { python3 -m crowd.bbox.project --run "$BBOX_RUN" "$@"; }
bbox watch --interval 30
```

`watch` отслеживает все загруженные пулы, включая `staged_batches`: показывает
их реальные статусы, число выданных и принятых страниц, оценивает экзамены и
ханипоты. Закрытие пула не останавливает процесс: поздние ответы тоже проверяются.
Процесс не открывает, не закрывает и не перезагружает пулы. Порог берётся из
`inputs.json` выбранного запуска; изменение общего `config.json` не меняет
ранее созданные проекты.

Откройте обучение и экзамен, затем пилот. После завершения пилота выгрузите
ответы и проверьте все 40 рабочих фотографий:

```bash
bbox export
```

Только после проверки пилота открывайте основной пул. При ручном открытии
`watch` не блокирует преждевременный запуск и не настраивает исключения показа
знакомых ханипотов. Если исполнитель повторно увидел контроль, его ответ не
считается независимой проверкой: он помечается для ручного разбора, а рабочие
ответы автора попадают в `required_audits`.

После завершения рабочих пулов выполните:

```bash
bbox export --require-complete
```

Команда заново получает ответы и пересчитывает экзамены и контроли. Она проверяет,
что все рабочие пулы закрыты, нет незавершённых страниц и получены ответы на все
400 фотографий. При неполном сборе завершится с ошибкой, но сохранит частичную
выгрузку для разбора. Файлы перечислены в разделе «Итоговая выгрузка».

`coverage.json` содержит реальные состояния пулов, `collection_complete` и
`required_audits`. Полный сбор не означает готовый golden set: ошибки загрузки,
сомнения и качество рамок нужно проверить в отдельном review. В ручном сценарии
проверку результатов и решение о переходе к основному пулу фиксирует команда;
`audit`/`release` относятся к сценарию управления этапами через CLI ниже.

## 4. Обучение и экзамен

После проверки готовности откройте обучение в кабинете Яндекс Заданий.
Проверьте прохождение всех 10 примеров и переход к экзамену.
Ошибки обучения можно исправлять; рабочий допуск назначает только экзамен.

```bash
bbox open
bbox status
```

**`open` начинает платную выдачу.** Перед открытием запустите в отдельном
терминале (с теми же `BBOX_RUN` и токеном) автоматическую проверку:

```bash
bbox watch --interval 30
```

Команда сразу проверяет ответы, затем повторяет проверку через 30 секунд после
завершения предыдущего цикла. Экзамены оцениваются по мере поступления принятых
ответов; закрытия пула ждать не нужно. Ханипоты проверяются во всех активированных
рабочих пулах, включая поздние ответы и пулы, загруженные через `stage`,
даже если они открыты вручную в кабинете. Переходы между этапами остаются ручными:
выданный допуск сам по себе не открывает пилот или основной пул.

В логе есть время, результат экзамена, оценка каждого нового ханипота, снятие
допуска и итог каждого цикла. Для сохранения лога:

```bash
bbox watch --interval 30 2>&1 | tee -a "$BBOX_RUN/watch.log"
```

Запускайте только один процесс на каталог. Он перечитывает состояние перед
каждым циклом; между циклами доступны `close`, `audit` и `next-batch`.
При сетевой ошибке, HTTP 429 или 5xx проверка повторится. Ошибки авторизации,
данных и состояния останавливают процесс. Проверяйте лог; при длительном сбое
закройте пул. Остановка — **Ctrl+C**; она не закрывает пулы. Команда не открывает
пулы, не отправляет их на модерацию и не выполняет ручной аудит.

Когда сбор экзамена закончен:

```bash
bbox close
bbox score-exam
bbox export
```

`close` не отменяет уже выданные страницы. Дождитесь их завершения и повторите
оценку перед переходом к пилоту. Проверьте результаты и допуски через `status`.

Спорные ответы из `exam.json` разберите через `audit --file ПУТЬ`, затем
повторите `score-exam`. **Аудит доступен только для последнего пула** — закончите
его до `next-batch`. При нехватке допущенных людей пересмотрите план набора.

## 5. Пилот

Если пулы загружены через `stage`, команда `next-batch` выбирает существующий
пул и готовит страницы с допусками. Предварительные страницы остаются в нём
с перекрытием 0; повторно они не выдаются.

```bash
bbox next-batch
bbox moderate
```

Проверьте пилотный пул в кабинете, дождитесь модерации, затем выполните
`bbox open`. Во время работы держите запущенным `bbox watch`.
После выполнения всех страниц:

```bash
bbox close
bbox score-controls
bbox export
```

Проверьте **все рабочие ответы пилота** из `review.json`; запишите аудит
в `$BBOX_RUN/audits.json`. Сбои загрузки контролей из `controls.json` требуют
отдельного решения. Затем:

```bash
bbox audit --file "$BBOX_RUN/audits.json"
bbox score-controls
bbox release --reviewer 'Имя' --reason 'Выводы о качестве, расходах и сроках'
bbox status
```

В `--reason` укажите фактические выводы. Проверьте **`pilot.passed`**:
`release` завершает проверку, но не означает успешный пилот. При провале основной
пул блокируется; исправления и повторную проверку нужно согласовать отдельно.

## 6. Основной пул

После успешного пилота создайте пул на все оставшиеся фотографии:

```bash
bbox next-batch
bbox moderate
```

После проверки и модерации выполните `bbox open`. Оставьте `bbox watch`
работать в отдельном терминале; состояние проверяйте через `bbox status`.
Если процесс проверки остановился или найдены систематические ошибки,
закройте пул. После разбора продолжите тот же пул через `open`.

Завершите его по шагу 5: `close → score-controls → export → audit →
score-controls → release`. Аудит обязателен для ответов из `required_audits`
и неразобранных сбоев контролей; если таких нет, импорт аудита пропустите.
Все страницы должны быть выполнены до `release`.

## 7. Повторы и восстановление допуска — при необходимости

После `release` подготовьте `$BBOX_RUN/repeat_ids.json` — список ранее выданных
ID, например `["123", "456"]`, и создайте пул повторов:

```bash
bbox next-batch --repeat-ids "$BBOX_RUN/repeat_ids.json" --repeat-reason 'Причина повторной разметки'
```

Проведите его по шагу 6. Для восстановления допуска после ручного разбора
и `release` текущего пула:

```bash
bbox restore --worker 'ID' --reviewer 'Имя' --reason 'Основание восстановления'
```

## 8. Итоговая выгрузка

При управлении этапами через CLI после `release` выполните `bbox export`.
При ручном открытии пулов используйте `bbox export --require-complete`.
Результаты находятся в `$BBOX_RUN`:

| Файл | Назначение |
| --- | --- |
| `result.json` | Принятые рабочие ответы для просмотра командой |
| `index.html` | Фотографии и рамки из `result.json`, поиск по ID и увеличение |
| `review.json` | Рабочие ответы с рамками, авторами и аудитом — вход для review |
| `coverage.json` | Покрытие выборки и проблемные ответы |
| `assignments.json` | Исходные ответы API всех статусов |
| `exam.json`, `controls.json` | Ответы экзамена и контроля |
| `state.json` | Ресурсы, оценки, допуски и решения |
| `inputs.json`, `preflight.json` | Снимок входных данных и проверка изображений |

Проверьте **`missing: []` и `answered == expected`** в `coverage.json`.
Ответы из `issues` сопоставьте с `review.json` и передайте на разбор вместе
с рабочей выгрузкой. Покрытие не подтверждает качество; варианты ответов
и незавершённые попытки сохраняются. Это ещё не golden set.

Сохраните каталог запуска для отчёта и восстановления: `runs/` исключён из Git.
Банк эталонов и контрольные ответы оставьте у команды; токен в файлы не записывайте.

## Ошибки и проверки

- При таймауте создания или загрузки повторите ту же команду. Если результат
  неизвестен, выясните его в кабинете или API; не удаляйте `state.json`.
- При незавершённых страницах дождитесь ответов или откройте текущий пул
  для оставшихся заданий. Новый пул до завершения текущего не создаётся.
- Если `release` требует аудит, добавьте решения и повторите `score-controls`.
- При отказе по бюджету или доступности исполнителей пересмотрите план.
  Не запускайте несколько команд для одного каталога одновременно.

После изменения кода:

```bash
python3 -m pip install -r crowd/bbox/requirements-dev.txt
python3 -m unittest discover -s crowd/bbox/tests -v
node crowd/bbox/tests/test_training.cjs
node crowd/bbox/tests/test_adapter.cjs
ruff check crowd/bbox
ruff format --check crowd/bbox
```

Тесты не обращаются к платному API. Изменённый интерфейс проверьте также
в предпросмотре платформы до открытия пула.

После `bbox export` откройте `$BBOX_RUN/index.html` в браузере. Он показывает
принятые рабочие ответы из `result.json`: фотографии, рамки и выбранный ответ
(в том числе отсутствие бабочек, сомнение или ошибку загрузки). Команда обсуждает
разметку вне страницы — здесь нет оценок, редактирования и сохранения решений.
Для обновления повторите `export` и перезагрузите страницу. Для фотографий нужен интернет.
